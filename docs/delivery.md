## Что проверено

- Функциональная проверка на Windows/Python 3.12: **52 passed**, один PostgreSQL-тест пропущен в SQLite-прогоне и пройден отдельно на PostgreSQL.
- Полный функциональный прогон внутри финального Linux-контейнера: **52 passed, 1 skipped**; пропущен тот же отдельный PostgreSQL-тест. API и PostgreSQL healthy, worker работает. Демо-часы возвращены к реальному времени.
- Миграция `0001`: upgrade, сравнение схемы с моделями, downgrade и повторный upgrade на SQLite.
- PostgreSQL 17 в Docker: миграции и `alembic check`, конкурентный захват задания двумя обработчиками и запрос исходящей очереди с блокировками.
- Полная сборка Linux-контейнера. API проходит readiness healthcheck; worker пишет heartbeat.
- `scripts/demo_walkthrough.py` через реальное локальное HTTP API: привязка, календарь, опросы, ответ заглушки с источником, обращение, ответ HR, закрытие и возврат в опрос.
- Кабинет просмотрен в браузере: вход существующим учебным аккаунтом, сводка, список площадок, загрузка текущих настроек в форму.
- Локальный SQLite/mock throughput smoke: 500 событий и 500 доставок за 5.037 с, около 99.3 событий/с. Это измерение локального обработчика, не обещание скорости MAX/ML.
- Ruff: lint и форматирование исходников, тестов, миграций и скриптов.

Точное состояние последнего прогона сохраняется в передаваемой сводке. Наличие кода MAX-адаптера и контрактных тестов не означает, что обмен с настоящим MAX уже проверен: токен не предоставлен.

На локальном стенде уже выполнен walkthrough, поэтому учебный сотрудник привязан и часть этапов завершена. Это демонстрационные данные, а не чистая начальная база. Время можно вернуть к реальному во вкладке «Демо». Для последовательного нового показа создать ещё одного учебного сотрудника.

## Для коллеги, проверяющего MAX

1. Получить зарегистрированного бота, токен и доступ к управлению им.
2. Передать токен через приватный `.env`, задать имя бота.
3. Включить `transport=max`, выбрать polling для разработки или публичный HTTPS Webhook.
4. Привязать учебного сотрудника по одноразовой ссылке. Аналогично привязать учебного HR.
5. Проверить текст и кнопки, несколько вариантов ответа, файл/изображение, старую кнопку, `/ask`, `/hr`, `/reply`, `/close`, остановку и повторный запуск.
6. Для ошибки вложения убедиться в обработке `attachment.not.ready`. Для timeout сверить фактический чат с uncertain-отправкой.
7. Не использовать один токен сразу в нескольких polling-процессах. Не включать polling одновременно с Webhook.

## Передача ML-команде

Передать `docs/ml-contract.md`, `contracts/ml-v1.schema.json` и примеры запросов. Нужны `/v1/answer`, `/v1/analyze`, `/v1/documents`, `/v1/documents/{external_id}`. При подтверждении интерфейса настроить URL, ключ и `ml_mode=http`. Для другого формата изменить только HTTPML-адаптер, сохранив внутренние типы.

Оба PDF заказчика требуют OCR. В презентациях есть SmartArt и изображения. Нельзя объявлять документ проиндексированным, просто извлекая пустой текст скана.

## Решения, которые ещё согласует команда

- Реальные контакты и области ответственности HR/руководителей.
- Праздники, переносы, сменные графики и точные периоды сопровождения.
- Спорный срок опроса из XLSX и наборы вариантов по площадкам.
- Отсутствующие карты, расписания транспорта, изображения, планы и ссылки.
- Итоговый набор тем и правила HR-сигналов. Сейчас политика настраивается через API.
- Допустимый контур хранения и обработки документов/ответов, срок хранения, SSO.
- Формат передачи результатов хакатона и адрес публичной демонстрации.

Текущий кабинет — функциональный интерфейс прототипа. Для нового корпоративного frontend уже экспортирован OpenAPI-контракт. Кнопки редактирования сложных опросов не заменяют согласование их содержания: такие сценарии загружаются JSON-описанием.

## Границы текущей версии

Один worker обрабатывает фоновые задания и доставку. Масштабирование ML и доставки следует выполнять отдельными пулами с сериализацией по сотруднику и распределённым limiter; простое увеличение replicas не является поддерживаемой настройкой.

Предварительная версия сценария содержит 28 логических шагов и 7 опросов. Это нормализованный пример на основе XLSX, а не побайтовая копия всех реплик и изображений. Исходные 71 заполненная строка двух листов сохранены в `examples/source_scenario_rows.json` для сверки.

Поведение `answered` подтверждается доступными ID/версиями источников; смысловую точность ответа проверяет ML-команда. В production нельзя использовать stub-анализ как оценку реального сотрудника.
