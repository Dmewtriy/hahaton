# Корсик: backend для адаптации сотрудников в MAX

Python 3.12+, FastAPI, SQLAlchemy 2, Alembic. PostgreSQL 17 в контейнерах, SQLite для локальной разработки. Фоновые задания, входящие события и исходящие сообщения хранятся в БД. Redis и Celery для этого прототипа не нужны.

Бот работает через реальный MAX API или локальный симулятор. RAG и анализ обратной связи подключаются через отдельный HTTP-сервис; по умолчанию используется **явно обозначенная заглушка**. Реальных моделей внутри backend нет.

Для передачи коллегам: [короткая инструкция развёртывания](docs/deployment.md). В ней есть запуск только через Docker, подключение MAX, проверки и перенос существующей БД.

## Быстрый запуск без MAX

Открыть PowerShell **в этой папке `back`**. Виртуальное окружение `.venv` уже подготовлено на текущем компьютере. На другом компьютере сначала выполнить `py -3.12 -m venv .venv`.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
.\.venv\Scripts\python.exe -m pip install --no-deps -e .
.\.venv\Scripts\python.exe -m korsik.cli init --demo
.\.venv\Scripts\python.exe -m korsik.cli migrate
.\.venv\Scripts\python.exe -m korsik.cli seed-demo
.\.venv\Scripts\python.exe -m korsik.cli serve
```

`init` создаёт `.env` со случайными ключами и отказывается перезаписывать существующий файл. `seed-demo` также не перезаписывает данные. Если эти команды уже выполнялись, повторять их не надо.

В другом терминале из той же папки:

```powershell
.\.venv\Scripts\python.exe -m korsik.cli worker
```

- Кабинет: <http://127.0.0.1:8000/dashboard>
- Swagger: <http://127.0.0.1:8000/docs>
- Готовность API: <http://127.0.0.1:8000/health/ready>
- `data/demo_credentials.json`: ключи тестового HR, руководителя, руководителя HR, приглашение сотрудника.
- `KORSIK_BOOTSTRAP_TOKEN` в `.env`: ключ **управления доступом**, без рабочих ролей.

Для работы с данными войдите **ключом HR** из `data/demo_credentials.json`. Bootstrap открывает только аккаунты и технические настройки: рабочие данные ему не доступны. Если нужны проверки без MAX, используйте `pytest`, Swagger и HTTP-симулятор `/api/demo/events` в отдельной базе с `transport=mock` и `enable_demo=true`. Инструкция HR: [docs/hr-guide.md](docs/hr-guide.md).

Вопрос `/ask Как открыть портал?` даёт ответ **учебной ML-заглушки** со ссылкой на учебный документ. Для остальных вопросов бот честно сообщает об отсутствии подтверждённого ответа и автоматически переводит диалог закреплённому HR. Маркер `DEMO:RED_FLAG` в свободном ответе воспроизводит тестовый HR-сигнал. Заглушка не оценивает настоящие настроения и не выполняет OCR/RAG.

## Контейнеры для коллег

Нужен работающий Docker Desktop / Docker Engine. `.env` создаётся командой `init`; в нём уже есть `POSTGRES_PASSWORD`.

```powershell
docker compose up -d --build
docker compose exec api python -m korsik.cli seed-demo
docker compose logs -f api worker
```

При запуске сначала поднимается PostgreSQL, затем одноразовый контейнер миграций, затем API и worker. БД и документы сохраняются в именованных volumes. Кабинет доступен на том же адресе. Ключи контейнерного демо находятся внутри volume:

```powershell
docker compose exec api python -c "from pathlib import Path; print(Path('/app/data/demo_credentials.json').read_text())"
```

Команда выводит секреты в ваш локальный терминал: не прикладывайте её вывод к публичным материалам. `docker compose down` останавливает стенд. Не добавляйте `-v`, если данные надо сохранить.

## Новые площадки и регламенты без разработчика

1. Войти рабочим ключом HR с областью соответствующей площадки либо `hr_head` с областью `*`.
2. В «Площадки» задать код, название, IANA timezone, рабочие дни, праздники и дополнительные рабочие даты. Добавить ссылки на карту, питание, транспорт и портал.
3. В «Адаптация» создать сценарий в визуальном редакторе. В нём доступны сообщения, опросы, напоминания руководителю, сроки, материалы и ручные шаги. Затем выбрать сценарий по названию в настройках площадки. JSON-импорт по API также сохранён.
4. В «Документы» загрузить регламент, указав площадки, категории и версию. Статусы: `pending`, `processing`, `ready`, `failed`; в режиме заглушки — `ready_stub`.
5. Для замены нажать «Загрузить новую версию»; предыдущий документ автоматически попадёт в архив. Удаление и восстановление доступны в интерфейсе. Деактивация немедленно исключает старый документ из разрешённых источников, даже если внешний индекс ещё его содержит.

Сценарии неизменяемые. Изменение расписания площадки отменяет только будущие/ожидающие шаги и создаёт новую ревизию. Выполненные шаги с тем же `id` не повторяются. Уже начавшийся опрос продолжает работать по сохранённому снимку своей версии.

HR может создавать собственные опросники и независимые рассылки: всем доступным сотрудникам, выбранным площадкам, подразделениям либо конкретным людям. Перед запуском показываются получатели; публикация требует отдельного подтверждения. Вопросы и состав опубликованной рассылки фиксируются снимком. Изменение даты выхода не переносит независимую рассылку HR.

## Роли и доступ

| Роль / право | Разрешения |
|---|---|
| `employee` | Свои данные, свои опросы и обращения, разрешённые документы |
| `hr` | Главный бизнес-администратор в своей области: сотрудники, рабочие аккаунты/роли, площадки, подразделения, документы, сценарии, опросы, рассылки и обращения. Область `*` — вся компания |
| `manager` | Статус только своих подчинённых и напоминания о встречах; без исходных комментариев и индивидуального анализа настроений |
| `hr_head` | Права HR в назначенной области, аналитика, еженедельный дайджест; глобальные политики при области `*` |
| `manage_access` | Отдельное право создавать аккаунты, назначать роли и области, блокировать доступ, выпускать ключи и сбрасывать привязку MAX |

Роль и область проверяются одновременно. `*` означает все площадки. Bootstrap не является HR и не читает ответы сотрудников. Включённый demo-режим отдельно разрешает bootstrap-ключу использовать симулятор и видеть тестовую исходящую очередь; поэтому его включают **только в изолированном стенде**.

API использует Bearer-ключи. В БД сохраняется SHA-256 случайного высокоэнтропийного ключа. Ключ нового аккаунта выдаётся один раз. `PUT /api/identities/{id}` меняет роли, область и активность; `POST .../rotate-key` отзывает старый ключ. Это практичный вход для прототипа; корпоративный SSO можно добавить отдельным адаптером авторизации.

Приглашения одноразовые, ограничены сроком и хранятся в хешированном виде. Повторный выпуск отзывает прежнее приглашение. Один аккаунт MAX нельзя привязать к двум сотрудникам. Для смены аккаунта HR своей области или доверенный администратор выполняет `POST /api/identities/{id}/unbind`, затем выпускает новое приглашение. Служебные аккаунты HR тоже можно привязать приглашением и отвечать в MAX командами `/reply ID текст`, `/close ID`, `/dashboard`.

## Календарь и опросы

Даты считаются относительно выхода или явно указанного окончания адаптации. Три месяца по умолчанию — **настраиваемый период сопровождения**, а не автоматическое решение о юридическом испытательном сроке. В API можно передать точную конечную дату.

- Календарные дни, календарные месяцы, N-й рабочий день, время площадки; праздники и рабочие переносы задаёт HR.
- Часовой пояс хранится у сотрудника и фиксируется при создании. Изменение зоны площадки не переносит существующих сотрудников в другую зону автоматически.
- Изменение даты выхода пересчитывает будущие шаги. Ручные шаги запускает HR своей области через `POST /api/steps/{id}/trigger`.
- Активный опрос задерживает следующие шаги опросов. Переписка HR не занимает этот слот. Ожидающие шаги идут по дате и коду. После освобождения диалога очередь продолжается.
- Типы вопросов: одиночный выбор, несколько вариантов, целая числовая оценка, текст. Для множественного выбора кнопки переключают варианты, `/done` завершает выбор.
- `comment_below: 8` запрашивает комментарий при 1–7. Вариант ответа может отдельно требовать комментарий, показать пояснение и уведомить HR.
- Промежуточные ответы и состояние комментария хранятся в БД. `/ask вопрос` или `/ask`, затем вопрос, сохраняет позицию опроса. После подтверждённого ответа или уточнения ML опрос продолжается; при неизвестном ответе вопрос автоматически передаётся HR, а опрос может продолжаться независимо от обращения.
- Напоминания по умолчанию на следующий день и ещё через день. Завершённым опросам напоминания не отправляются; HR-переписка не останавливает напоминания.
- `/hr текст` отправляет одно сообщение HR. `/hr` без текста или кнопка «Ответить HR» подготавливают следующее сообщение; `/cancel` отменяет ввод, `/resume` возвращает к опросу. Обращение не блокирует расписание. В «Переписка HR» — сотрудники, единая история и красные индикаторы непрочитанного.

`PUT /api/demo/clock` с ISO datetime управляет временем; `{"now": null}` возвращает реальное. Lease фоновых задач измеряется реальным временем. Production запрещает demo endpoints и не запускается с сохранённым тестовым временем.

## ML, эскалации и документы

Контракт команды описан в `docs/ml-contract.md` и `contracts/ml-v1.schema.json`. Это подготовленный backend-контракт v1, который надо передать ML-коллегам для подтверждения.

```dotenv
KORSIK_ML_MODE=http
KORSIK_ML_BASE_URL=https://your-ml-service
KORSIK_ML_TOKEN=your-private-service-key
KORSIK_ML_TIMEOUT_SECONDS=15
```

В сервис передаются разрешённые ID и версии документов, площадка/категория, ограниченная история и контекст текущего шага. Ответ `answered` без источников либо с недоступным/неактивным/неверной версии источником блокируется. Это проверка доступа и происхождения, а не доказательство смысловой корректности ответа: grounding и ML-оценку выполняет команда ML.

Свободные ответы и условные комментарии анализируются отдельными заданиями. Результат сохраняется с версией обработчика. Политика `/api/policies/escalation` определяет минимальный риск и фильтр тем. Структурный сигнал варианта ответа и ML-сигнал одного ответа используют общий ключ обращения, чтобы не создавать дубли.

Загрузка регламента сохраняет оригинал и метаданные, затем отправляет его внешнему индексатору. Асинхронная индексация опрашивается до двух часов; ошибки и повторные попытки видны через статус документа и операции очереди. OCR сканов и чтение SmartArt/изображений — ответственность индексатора. Загруженные файлы не публикуются через открытый static URL: скачивание требует авторизации и проверки области.

## Аналитика и интерфейс

`GET /api/dashboard?start=...&end=...` — контракт дашборда. Обе даты с часовым поясом, интервал `[start, end)`. Без параметров — последние семь дней. Числа считает backend из сохранённых сущностей:

- сотрудники и текущие этапы;
- активные и завершённые опросы;
- запланированные сообщения;
- открытые и новые обращения;
- обработанные ответы, темы, распределение настроений и рисков;
- количество и статусы вопросов к RAG;
- средние числовые оценки с количеством ответов; учитываются сохранённые ответы, включая ещё не завершённые опросы.

Текущие остатки (активные опросы/открытые обращения) показываются на момент запроса, а не на историческую дату `end`. За период считаются новые/завершённые события. Темы считаются по ответам: один ответ даёт теме не более одного попадания. Демо-анализы отмечаются отдельно.

По понедельникам в 09:00 Europe/Moscow руководители HR получают сводку за предыдущие семь дней; часовой пояс, день и час настраиваются в «Настройки → Еженедельный дайджест» глобальным HR или через `/api/policies/digest`. На первом запуске после времени рассылки формируется один дайджест текущей недели. Личные комментарии в дайджест не включаются.

## MAX Mini App

Кабинет обслуживается тем же backend: `/app` — точка входа мини-приложения, `/dashboard` — локальный адрес. Сервер проверяет HMAC-подпись MAX, срок запуска, привязку аккаунта, действующие административные права и область каждой операции. Сотрудник или руководитель без прав HR не получает административные данные даже по прямой ссылке.

Пока используется только локальный запуск. Для открытия внутри MAX:

1. Разместить backend на публичном HTTPS-адресе.
2. В существующем `.env` задать `KORSIK_WEBAPP_PUBLIC_URL=https://your-domain/app`.
3. В настройках бота на платформе MAX для партнёров зарегистрировать этот URL.
4. Привязать HR к его MAX-аккаунту по приглашению. Команда `/admin` выдаёт кнопку только администратору.

Нативную общую кнопку MAX после регистрации платформа может показывать всем; содержание кабинета и API всё равно защищены серверной авторизацией. Для файлов используется `WebApp.downloadFile` с отдельной ссылкой на один документ сроком 60 секунд и повторной проверкой доступа. В обычном браузере работает авторизованное скачивание.

В production вход локальным ключом выключен. В разработке ключ и короткая сессия остаются в памяти вкладки, не в localStorage.

Официальная документация: [подключение и диплинки](https://dev.max.ru/docs/webapps/introduction), [валидация запуска](https://dev.max.ru/docs/webapps/validation), [MAX Bridge](https://dev.max.ru/docs/webapps/bridge). Архитектура: [docs/architecture-v2.md](docs/architecture-v2.md).

## Реальный MAX

Понадобится зарегистрированный бот и токен от коллег/организаторов. Устанавливать MAX разработчику не требуется. По официальной документации доступ к созданию бота связан с верификацией и модерацией.

```dotenv
KORSIK_TRANSPORT=max
KORSIK_MAX_TOKEN=your-bot-token
KORSIK_MAX_BOT_NAME=your_bot_name
KORSIK_MAX_CA_FILE=certs/russian_trusted_root_ca.pem
```

Для разработки отдельно запустить `python -m korsik.cli poll` или `docker compose --profile max-poll up -d`. Постоянный worker также должен работать. Активный Webhook и polling одновременно не используются.

Имя бота задаётся без `@`. При настройке изменяйте нужные строки существующего `.env`, сохраняя `POSTGRES_PASSWORD` и `KORSIK_BOOTSTRAP_TOKEN`. Для уже созданной PostgreSQL-базы используется прежний пароль. Публичный сертификат для MAX включён в `certs/`; подробности и отпечаток — в `certs/README.md`.

Для Webhook нужен публичный HTTPS на 443 с доверенным сертификатом. Reverse proxy перенаправляет `/webhooks/max` на API. Запрос сначала сохраняется в БД, ответ MAX не ждёт ML. Регистрация:

```powershell
python -m korsik.cli subscribe https://your-domain/webhooks/max
```

Проверяется `X-Max-Bot-Api-Secret`. Сообщения из групп игнорируются: онбординг содержит личные данные. Используется `Authorization: token`, текущий базовый адрес `https://platform-api2.max.ru`; при необходимости добавить согласованный CA bundle через `KORSIK_MAX_CA_FILE`, не отключая TLS-проверку.

Вложения загружаются по выданному MAX URL, токен сохраняется для повторного использования. Ошибка `attachment.not.ready` повторяется с задержкой. Длинные сообщения разбиваются на части. Единственный процесс worker ограничивает отправки до безопасной скорости.

Официальные источники: [подготовка](https://dev.max.ru/docs/chatbots/bots-coding/prepare), [события](https://dev.max.ru/docs-api/methods/GET/updates), [Webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions), [сообщения](https://dev.max.ru/docs-api/methods/POST/messages), [загрузка файлов](https://dev.max.ru/docs-api/methods/POST/uploads).

## Устойчивость и эксплуатация

Схема: `docs/architecture.md`. Приложение развёртывается с **одним worker**; несколько HTTP-процессов возможны с PostgreSQL. Очередь хранит unique dedupe keys, attempts, lease, статусы и безопасный класс ошибки. Выполнение логики и создание исходящих сообщений проходят в общей транзакции.

Гарантия exactly-once для внешнего MAX API недостижима без поддержки идемпотентности провайдером. Поэтому timeout после отправки или падение отправителя дают `outbox.status=uncertain`: автоматический повтор запрещён. Оператор сверяет диалог и явно решает, считать отправленным или повторить. Это предотвращает тихие дубли ценой ручной обработки редких неопределённых отправок.

`/api/operations` показывает состояния очередей и heartbeat; `/api/audit` — изменения доступа/конфигурации. Технические логи содержат ID операции, шаблон маршрута, статус и класс ошибки, без тел сообщений, ключей и query strings. PostgreSQL и volume документов нужно резервировать вместе. `.env`, `data/` и `.venv` исключены из Git и сборки образа.

`GET /api/operations/jobs` и `.../deliveries` возвращают проблемные операции без личного содержимого. Failed-задание можно повторить через `POST /api/operations/jobs/{id}/retry`. Неопределённую отправку оператор разрешает через `POST /api/operations/deliveries/{id}/resolve`: `{"action":"mark_sent"}` или `{"action":"retry","accept_possible_duplicate":true}` после сверки чата.

Для production использовать отдельную БД и volume, реальные MAX/ML, собственный TLS reverse proxy и `compose.production.yaml`. Не переключать демо с тестовыми сотрудниками в рабочую базу. Секреты не загружать в публичный репозиторий. Корпоративная аутентификация, политика хранения и SSO согласуются перед реальным внедрением.

## Проверка

```powershell
python -m pytest -q

python -m ruff format --check src tests scripts migrations
python scripts/load_smoke.py --events 500
python scripts/demo_walkthrough.py
```

`demo_walkthrough.py` проверяет путь через настоящее локальное HTTP API с учебными аккаунтами. Скрипт требует запущенный API, `enable_demo=true` и выполненный seed-demo; может менять тестовое время и прогресс учебного сотрудника. Для повторяемой чистой проверки используйте тесты.

`tests/test_postgres.py` запускается только с `KORSIK_TEST_DATABASE_URL` на отдельной тестовой БД. CI проверяет PostgreSQL-миграции и совместимость. Локальная нагрузочная проверка с заглушками не измеряет пропускную способность настоящего MAX или ML.

Состояние этапов и открытые вопросы: `docs/delivery.md`. Реальный обмен с MAX, качество RAG и анализ реальных ответов требуют предоставленных командой доступов и ML-сервиса.

## Подсказки команд MAX

После настройки действующего токена: `docker compose exec api python -m korsik.cli sync-commands`. Список команд сохраняется в MAX и появляется при вводе `/`; описания на русском. Предыдущий список сохраняется в `data/backups` контейнера. На текущем стенде команда выполнена при обновлении. Служебные `/admin`, `/reply`, `/close`, `/dashboard` проверяют права независимо от меню. Документация: https://dev.max.ru/docs-api/methods/PATCH/me/commands .
